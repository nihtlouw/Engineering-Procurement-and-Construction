## 0. Ringkasan kondisi project

**Verdict: demo-grade / pilot-ready, BUKAN production-ready. Monolit, tetapi belum modular.**

Aplikasi ini bukan "aplikasi kosong": sudah ada produk EPC yang cukup dalam di sisi **cost control & finance** (DPP/PPN, retensi, termin, PO, expense + OCR, invoice + PPh, change order, stage gate 9 tahap, BAST 1/2, punch list, audit trail, dokumen PDF). Kualitas domain dan UI-nya di atas rata-rata prototype. Namun:

1. **Aplikasi hanya bisa berjalan di atas data seed.** Tidak ada satu pun endpoint/UI untuk membuat proyek, klien, site, anggota, RAB, termin, maupun item jadwal. 24 route API seluruhnya mutasi/read terhadap data yang sudah di-seed.
2. **Data perusahaan tidak berada di akun perusahaan.** Tidak ada `companies`, `memberships`, `company_id`, RLS, maupun Supabase. `company_settings` adalah satu baris global; `users` adalah akun personal global dengan role global. Ini bertentangan langsung dengan prinsip yang Anda tetapkan.
3. **Ada 3 blocker keamanan aktif** (auto-seed produksi + password demo, payload SSR berlebih, secret file dengan fallback yang dapat ditebak) dan **build produksi gagal tanpa `DATABASE_URL`** (terverifikasi).
4. **6 dari 9 modul MVP yang Anda minta belum ada**, dan 3 sisanya baru sebatas fondasi parsial.
5. **Utang teknis terukur:** 0 test, 0 CI, 0 migrasi berversi, 7 error lint, 1 critical + 2 high dependency, 100 baris kode > 400 karakter (terpanjang 5.955 karakter), 25 query full-table per request.

Repo juga sudah memuat **4 set dokumen analisis lama** (`analisis/`, `docs/`, `design/`, `tools/`) dengan 46+ temuan. Sebagian besar **masih valid**, sebagian **sudah usang** (mis. dokumen lama mengklaim `error.tsx`/`loading.tsx` belum ada — faktanya sudah ada; renderer PDF dan error handler pool sudah diperbaiki). Audit ini memverifikasi ulang kondisi **hari ini**, bukan mengulang dokumen lama.

## 4. Rekomendasi arsitektur: modular monolith

**Keputusan: tetap SATU aplikasi, SATU database, SATU deploy.** 9 modul dibatasi oleh folder + kontrak import, bukan dipisah menjadi service/aplikasi. Alasan: semua modul berbagi agregat `project`, transaksi lintas modul (foto → laporan → dokumen → audit), tim kecil, dan regulasi/isolasi datanya identik. Pemisahan baru relevan jika ada regulasi berbeda, tim ≥ 3 squad, atau beban OCR/PDF yang mengganggu request path (lihat §8).

### 4.1 Prinsip

1. **Module-first, route-last.** Setiap modul punya `schema.ts`, `types.ts`, `service.ts` (aturan bisnis murni, mudah ditest), `actions.ts` (server action / route handler), `ui/`, dan `*.test.ts`.
2. **Satu arah ketergantungan:** `ui → actions → service → db`. Modul lain diakses lewat **kontrak publik** (`modules/<nama>/index.ts`), bukan import langsung ke tabel/`schema.ts` modul lain. `shared/` hanya berisi lintas-modul (auth, errors, validation, formatting, storage, audit).
3. **Company scope di database, bukan hanya di aplikasi.** `company_id` di setiap tabel bisnis + RLS. Aplikasi tetap melakukan `requireCompany()` sebagai defense-in-depth.
4. **Migrasi berversi wajib** (`drizzle/NNNN_*.sql`), `push` hanya untuk dev lokal. Semua perubahan skema lewat PR + CI.
5. **Setiap vertical slice wajib:** migrasi + types + validasi Zod + error handling + minimal test + acceptance criteria (aturan Anda #3).
6. **Tidak ada secret di kode**, env divalidasi saat boot (fail fast), `.env.example` hanya placeholder.
7. **Tanpa scraping marketplace**; Price Reference murni input manual/API resmi/afiliasi.

### 4.2 Struktur target

```

├── app/
│   ├── (app)/
│   │   ├── page.tsx                    # dashboard
```

### 4.3 Keputusan data & auth (dua opsi, harus dipilih sebelum Sprint 1)

| | **Opsi A — Minim invasif (direkomendasikan)** | **Opsi B — Supabase penuh** |
|---|---|---|
| DB | Tetap Neon/Postgres + Drizzle + `pg` | Migrasi ke Supabase Postgres |
| Auth | Tetap sesi DB custom; RLS via `SET LOCAL app.current_company_id` dalam transaksi | Supabase Auth + JWT claim `company_id` → RLS native |
| Storage | Supabase Storage / S3-compatible (hanya object storage) | Supabase Storage |
| Risiko | Perlu disiplin: **semua** query harus lewat helper transaksi ber-scope; jika ada yang lupa, RLS menolak (fail-closed) | Migrasi auth memutus seluruh sesi & `passwordHash` scrypt; butuh backfill user; coupling lebih kuat |
| Effort | M (2–3 minggu) | L (4–6 minggu) |

**Rekomendasi: Opsi A** untuk MVP 1. Anda mendapat isolasi company + RLS + object storage tanpa membuang 28 tabel dan logika domain yang sudah benar. Opsi B tetap terbuka nanti (RLS policies-nya kompatibel).

### 4.4 Komponen lintas modul

- **RLS:** `ENABLE ROW LEVEL SECURITY` + `FORCE` pada tabel bisnis; policy `USING (company_id = current_setting('app.current_company_id')::uuid)`; role `CLIENT_VIEWER` mendapat policy read-only terbatas pada proyek yang di-share; `service_role` hanya untuk job migrasi/seed.
- **Storage:** bucket privat per company (`company/{company_id}/projects/{project_id}/...`), presigned upload, magic-byte + MIME + ukuran, kompresi di client, AV/kuota menyusul. `file_objects` menjadi metadata saja; backfill base64 lama (lihat risiko §8).
- **Document Generator:** template DOCX disimpan di object storage, definisi & mapping variabel di `document_templates` + `template_variables` (DB/admin). Library: **`docxtemplater` + `pizzip`/`JSZip`** untuk DOCX (serverless-friendly, murni JS, tanpa Chromium), **`pdf-lib`** yang sudah ada untuk PDF langsung dari snapshot (bukan konversi DOCX→PDF via headless browser — tidak kompatibel Vercel). Modul `field-photos` menyuplai `{{#photos}}` ke laporan dokumentasi.
- **Audit:** `audit_logs` dengan `company_id`, `actor_id`, `action`, `object`, `diff`, `created_at`; trigger DB melarang UPDATE/DELETE; audit login, unduh file, generate dokumen.
- **Dashboard:** satu query agregat SQL per company (`COUNT FILTER`, `LATERAL`, materialized view ringan bila perlu), bukan 25 `select *`; polling 30–60 detik / `router.refresh()`.

### 4.5 Transisi bertahap (tanpa Big Bang)

1. Sprint 1 menambah `companies`/`memberships`/`company_id` + backfill **satu** company untuk data yang sudah ada, sambil **mempertahankan** 24 route lama tetap berfungsi.
2. Modul baru dibangun **berdampingan** di `src/modules/*`; route lama perlahan dialihkan ke service modul (strangler), bukan ditulis ulang sekaligus.
3. `getWorkspaceData()` dipecah per modul; UI lama tetap menerima `AppData` sementara (adapter) sampai semua view bermigrasi ke URL route.
4. Setiap sprint punya feature flag / rollout per company, sehingga UAT bisa dilakukan tanpa mengganggu data demo.

## 8. Risiko teknis yang harus dijelaskan sebelum eksekusi

1. **RLS + connection pool (risiko tertinggi).** `SET LOCAL app.current_company_id` hanya berlaku **di dalam satu transaksi**. `getWorkspaceData()` saat ini menjalankan 25 query `Promise.all` di luar transaksi — jika RLS diaktifkan tanpa mengubah pola ini, semua query akan gagal atau (lebih buruk) mengembalikan data company lain bila memakai `SET` (bukan `SET LOCAL`). Mitigasi: helper `withCompany(companyId, tx => ...)` wajib, satu transaksi per request, policy `FORCE ROW LEVEL SECURITY`, dan tes integrasi "company A tidak bisa baca company B" di CI.
2. **Backfill data yang sudah ada.** 28 tabel berisi seed demo "PT Ardaya Energi Sistem" tanpa `company_id`. Perlu migrasi `NOT NULL` bertahap: `nullable → backfill satu company → SET NOT NULL → RLS`. Jangan `ALTER ... NOT NULL` langsung. Perlu keputusan: **apakah data demo produksi di-reset atau dimigrasi**.
3. **Migrasi file base64 → object storage.** `file_objects.content_base64` berisi PDF/gambar nyata. Perlu job backfill + dual-read (`contentBase64 ?? storageKey`) selama transisi, dan `storageKey` saat ini berformat `private/{user.id}/...` yang **tidak mengandung company/project** — harus direnormalisasi agar policy storage bisa diterapkan.
4. **PDF dari DOCX di Vercel.** Konversi DOCX→PDF umumnya butuh LibreOffice/Chromium (tidak tersedia di fungsi serverless standar). Rekomendasi: **dua jalur** — DOCX dari template (`docxtemplater`), PDF langsung dari snapshot yang sama via `pdf-lib`. Jika PDF harus identik pixel-per-pixel dengan DOCX, siapkan layanan konversi eksternal berbayar + antrean (di luar MVP 1).
5. **OCR `tesseract.js` di request path** (`maxDuration = 60`, unduh traineddata saat runtime) berisiko timeout/DoS & biaya. Saat Field Photos masuk, pindahkan OCR ke antrean/background job atau beri rate limit + kuota.
6. **Vercel body limit.** Kode mengizinkan upload 25 MB base64; platform serverless umumnya membatasi body request jauh di bawah itu. Nilai pastinya bergantung konfigurasi akun Anda — **verifikasi di Vercel** sebelum menetapkan batas; presigned upload menghilangkan masalah ini sekaligus.
7. **Perubahan auth = sesi terputus.** Bila memilih Opsi B (Supabase Auth), seluruh `passwordHash` scrypt dan tabel `sessions` harus dimigrasikan/dibuang; semua pengguna wajib reset password. Opsi A menghindari ini.
8. **Regresi UI lama saat memecah `AppData`.** 10 komponen client bergantung pada satu objek raksasa; gunakan adapter + migrasi per view, jangan refactor sekaligus.
9. **Dokumen lama menyesatkan.** `analisis/*.csv` berisi status "sudah diperbaiki"/"belum ada" yang tidak lagi akurat. Jadikan audit ini satu-satunya baseline; arsipkan yang lama dengan label `superseded`.

1. **Opsi A (tetap Neon + Drizzle + sesi custom + RLS via `SET LOCAL`) atau Opsi B (Supabase Auth + RLS JWT)?** Rekomendasi saya: **A**.
2. **Data demo di lingkungan live: di-reset total atau dimigrasi menjadi company pertama?** (Berpengaruh pada migrasi backfill & akun.)

## 10. Addendum — Budgeting & Pekerjaan Tambah/Kurang (PTK)

*Ditambahkan 2026-11-17 menindaklanjuti pertanyaan: "apakah kamu juga mengantisipasi tentang budgeting, bisa ada pekerjaan tambahan atau kurang?"*

Dua makna yang dijawab sekaligus: **(A)** apakah estimasi pengembangan sudah mengantisipasi lingkup budgeting; **(B)** apakah model data sudah mengantisipasi **pekerjaan tambah/kurang / variation order** yang mengubah anggaran & kontrak. Jawaban singkat: **A kurang dalam, B belum memadai.**

### 10.1 Yang SUDAH saya antisipasi (jangan dihitung dua kali)

- S2 "Buat proyek baru → RAB → PO → termin": migrasi `po_items`/`rab_items`, CRUD RAB client & internal, baseline, approval, ekspor XLSX.
- Masalah #8: overbudget, over-invoicing, dual source nilai kontrak, kategori CO hardcode, penomoran UTC.
- `finance.ts` sudah memisahkan **rencana / komitmen / realisasi** dengan benar: `baselineInternal`, `commitment`, `remainingCommitment`, `actualCost`, `pendingCost`, `forecastExposure`, `remainingBudget`, `indicativeMargin`, `retentionOutstanding` — memakai `Decimal`, bukan float. **Ini aset, jangan ditulis ulang.**
- `budget_version_unique (project, type, version_no)`, `merge_snapshot` dokumen, template `RAB_CLIENT`, `export/budget`, stage gate & close-check.

### 10.3 Khusus: Pekerjaan Tambah / Kurang (PTK / Variation Order)

Model saat ini **hanya bisa menambah**, dan itu pun belum tuntas:

| Kebutuhan PTK | Kondisi sekarang | Bukti |
|---|---|---|
| Dampak **waktu negatif** (pekerjaan kurang → jadwal lebih cepat) | **Diblokir**: `timeImpactDays: z.number().int().min(0)`; `IMPLEMENT_CHANGE_ORDER` selalu `setDate(+timeImpactDays)` | `change-orders/route.ts:8`, `projects/[id]/action:89-90` |
| Dampak **harga/biaya negatif** | Bisa masuk ke DB (`z.string()` tanpa cek tanda), tapi tidak ada validasi, tidak ada batas "nilai kontrak tidak boleh ≤ 0", dan `IMPLEMENT_CHANGE_ORDER` menyisipkan baris RAB dengan `unitAmount`/`total` negatif tanpa penanda | `change-orders/route.ts:8`, `projects/[id]/action:84-85` |
| **Pos RAB yang dihapus** (pekerjaan kurang = lingkup dicoret) | CO hanya **menambah** 1 baris `CO-<kode>`; tidak ada `omitted_line_id` / status `REMOVED` pada `budget_lines` | `projects/[id]/action:81-86` |
| **Jenis perubahan** (TAMBAH / KURANG / SUBSTITUSI) | Tidak ada kolom `variation_type`; `LABELS` tidak punya istilah PTK | `schema.ts:350-360`, `domain.ts` |

### 10.5 Definisi MVP Budgeting yang saya rekomendasikan

**IN (wajib S1–S2):** `rab_items` + `po_items`; CRUD & approval versi RAB client/internal; baseline immutable + partial unique index; pagu per pos dengan blokir/approval overbudget; validasi `budgetLineId` lintas proyek; **satu** sumber nilai kontrak; `variation_orders` ADD/OMIT/SUBSTITUTE signed; `wbs_item_id` + phasing nilai per periode; policy RLS internal-vs-client; tes `Decimal` (pagu 110%, PTK negatif, baseline tunggal); audit diff revisi RAB.
